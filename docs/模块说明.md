## 单机回归

退出已在运行的 `room_server` / `relay_server` / `client_transfer` 后执行：

```bash
make -B test-transfer
```

同时出现 `ALL STREAM TESTS PASS` 与 `ALL TRANSFER INTEGRATION TESTS PASS`。测试自行起停子进程，占用 TCP 37401/37405、UDP 37402/37404。证据目录不提交进仓库。

Mac：Xcode Command Line Tools 与 Homebrew `openssl@3`。WSL：`build-essential`、`python3`、`libssl-dev`。

分项：

```bash
python3 -u tests/test_transfer.py --case tcp
python3 -u tests/test_transfer.py --case resume
python3 -u tests/test_transfer.py --case udp-once
python3 -u tests/test_transfer.py --case udp-all
python3 -u tests/test_transfer.py --case relay
python3 -u tests/test_transfer.py --case announce
```

| 用例 | 内容 |
|------|------|
| tcp | 三进程收发；Tracker 关闭、来源退出后仍完成；远端 HAVE 不令本机假完成 |
| resume | 重启复用缓存；损坏块重新校验 |
| udp-once | 丢选定子包，NAK 补齐，路径保持 UDP |
| udp-all | 丢全部 UDP 数据，有界重试后转 `relay_server` |
| relay | 完整文件经中继；粘包、错房间、伪造来源、慢接收方隔离 |
| announce | 本机 ANNOUNCE 到 37404。跨机器通告见实验 7 |

保留 `FAULT_DROP` 断言与既有超时。

### 案情板「状态」行

终端最后一行 **`状态：…`** 来自 `ui_state.status`，由 `ui_set_status` 维护，与 **`房间服务：在线/离线`**、**`阶段：…`** 独立。

| 场景 | 预期 |
|------|------|
| 启动后未 `join` | `状态：未进房`；`peer 0`；阶段多为「空闲」 |
| `JOIN_OK` 之后（`./client` 与 `./client_transfer`） | `状态：已进房 peer=N`（2026-11-04 起 transfer 与 client 一致） |
| 关房实验 D 窗 | 故意不 `join`，保持「未进房」直至通告路径 |
| 联调误判 | 若 **在线 + peer≥1 + 阶段非空闲** 已成立，以进房为准；旧版 transfer 曾只改 `phase` 不改 `status`，需 `make client_transfer` 后重进 |

Web 案情板读同一份 `ui_state.json` 时，`status` 字段含义相同。

## 背景

采用方案 A：房主端用 Python 生成器将一局落盘到 `session_<id>/`，C 侧仅装载
（`src/generate/generate.c`），不生成、不渲染图像。传块模块据此读取真实案卷字节。

本局三份证物（file_id）：`file_1` 现场勘查图（图）、`file_2` 证物登记卡（图）、
`file_3` 案卷正文（文本）。单文件 ≤ 512 KiB，逻辑分块 16384 B。

## 生成与自检

```bash
# 1) 生成一局（无 Pillow 依赖；内容是用种子派生的确定性字节，网络实验只关心字节与哈希）
python3 tools/gen_case.py [seed_hex] [base_dir]
#    -> base_dir/session_<id>/file_1 file_2 file_3 manifest.bin

# 2) C 侧自检：解析 manifest 并读块
gcc -o test_generate src/generate/generate.c src/generate/test_generate.c
./test_generate session_<id>

# 3) 哈希一致性校验（manifest 每块摘要 == 文件实切块哈希，transfer 校验依赖此）
python3 tests/check_manifest.py session_<id>     # 期望 HASH-CONSISTENCY: PASS
```

`session_*/` 由根目录 `.gitignore` 忽略，各机本地生成。

## C 接口（transfer 调用，见 `src/generate/generate.h`）

```c
int  gen_load_manifest(const char *session_dir, struct gen_manifest *m);
void gen_free_manifest(struct gen_manifest *m);
int  gen_read_piece(const struct gen_manifest *m, uint8_t file_id,
                    uint16_t piece_idx, uint8_t *out, size_t *out_len);
```

- `gen_load_manifest`：解析 `session_dir/manifest.bin`，填 `struct gen_manifest`
  （`session_id`、`seed_hash`、`file_n`，每个文件含 `file_size`、`file_hash`、
  `piece_count`、`pieces[].hash`、磁盘 `path`）。
- `gen_read_piece`：取第 `file_id` 个文件第 `piece_idx` 块的字节写入 `out`
  （`out` 至少 16384 B），`*out_len` 返回实际长度——**末块更短**，计算：
  `min(16384, file_size - piece_idx*16384)`。失败返回 -1（文件/块号越界）。
- 收方拿到块后，用 `m.files[k].pieces[piece_idx].hash` 比对 SHA-256 即可，无需自己算布局。

## 数据契约速查（v1 §5.4）

`manifest.bin` = 线上 `MANIFEST` 正文（大端）：

| 偏移 | 长度 | 字段 |
|------|------|------|
| 0 | 4 | `session_id` |
| 4 | 32 | `seed_hash`（不是种子） |
| 36 | 1 | `file_n`（本项目 3） |
| 37 起 | 每项 41 + `piece_count*32` | 文件项 |
| 文件项内 | | `file_id`(1) `chapter`(1) `kind`(1 图/2 文本) `file_size`(4) `file_sha256`(32) `piece_count`(2) `piece_hash × 32`（块号升序） |

落盘：`session_<id>/file_<file_id>`。块号从 0：`piece_count = ceil(file_size/16384)`。

## 实现约束

- 收块按 `pieces[piece_idx].hash` 校验；整文件按 `file_hash` 复核。  
- 末块不足 16384 字节时，发包与写盘使用实际长度。  
- `BITFIELD` / `HAVE` 的 `piece_count` 与清单一致（约定 §5.5 / §5.6）。  
- TCP 回整块；UDP 子包 1024 字节，末子包可短（约定 §5.7 / §5.8）。  
- 实验 8 中继计数仅含内层 `PIECE_DATA` 数据区，不含 `RELAY_WRAP` 头（约定 §5.12）。  
- 种子不进入 `MANIFEST`、日志与文件名；真凶仅出现在 `file_3` 正文。

## 1. 一句话结论

我原先以为"**进同一房间后，房主和侦探的剧情进度应该实时一致，房主推进、所有人跟着跳章**"。
核对源代码后发现**并不是这样实现的**：除成员名单外，**阶段 / 问答 / 指认都是各台机器的本地状态，互不广播**。
但这**不影响正常游玩与演示**——各端最终会各自走到同一结局，游戏可以完整通关，抓包也照常进行。

> 核对表没有要求房间内进度实时同步。
> 因此"进度不同步"属于**我的理解**，不是源代码违反了约定，也不是已交付功能的 bug。
> 这个文档想跟大家同步一下意见，就是要不要做同步，谁来做。

## 2. 我原先的理解 vs 源代码实际行为

| 事项 | 我原先以为 | 源代码实际行为 | 是否影响游玩 |
|------|------------|----------------|--------------|
| **阶段进度**（第一章/问答/第二章/指认/结束） | 房主推进，全员立刻跳到同一章 | 每台机器只看**本机**证物下没下齐、自己答没答对，独立推进本机 `phase`，不广播 | 否，各自走到下一阶段 |

## 3. 源代码依据（便于负责同学核对）

- **阶段本地推进**：`src/transfer/client_main.c` 的 `next` 分支（约 258–262 行），
  推进条件全部基于本机 `files[].have` / `answer_correct`，没有对外发送阶段消息：

  ```c
  if (phase==CH1    && 本机 file0、file1 都 have) 推进到 QUIZ;
  else if (phase==QUIZ && 本机 answer_correct==1) 推进到 CH2;
  else if (phase==CH2   && 本机 file2 已 have)     推进到 CHOICE;
  ```

- **成员名单才走服务器广播**：`src/tracker/room_server.c` 在加入/退出/反射更新时
  `push_peer_list()`；客户端在 `CMD_PEER_LIST` 分支 `members()` 更新（`client_main.c:85`）。
- **成员退出**：`members()` 收到 `PEER_LIST` / `JOIN_OK` 后，把本次名单里没有的旧成员清掉（`src/transfer/client_main.c`）。Tracker 掉线时收不到新名单，本机缓存保留，在途传块不受影响。
- **路径字段**：`path_type` 仅在下载方成功收块时写入（`src/transfer/transfer.c:283`）。
- **协议里没有"阶段同步"指令**：`include/common.h` 的 0x01–0x16 中无对应命令。

## 4. 为什么"不同步也能玩"

1. **P2P 分块本来就各端速度不同**：有人先下完先进第二章，有人后下完停在问答，是合理现象；下齐后自然到同一阶段。
2. **各端最终收敛到同一结局**：所有人都能独立完成 取块 → 问答 → 第二章 → 指认 → 结束，不依赖别人替自己推进。
3. **核心网络数据是真实往来的**：进度显示不同步只是 UI/本地状态层面，侦探↔房主的分块、信令流量真实走物理网卡，抓包目的不受影响。
4. **房主路径可以显示「未知」**：该字段是本机取块路径，房主自己不取块。不阻塞流程。
